Oh My Shell

An interactive Linux shell, written in Rust.

It behaves like a familiar POSIX shell, helps while you type (colors, hints, completion), keeps a searchable history, checks dangerous commands before they run, and can optionally hand a task to an AI. Nothing the AI suggests runs without a preview and your confirmation.

Install

Linux, x86_64 or aarch64, glibc 2.35 or newer (Ubuntu 22.04+, Debian 12+, Fedora 36+).

curl --proto '=https' --tlsv1.2 -fsSL \
  https://github.com/imshaid/oh-my-shell/releases/latest/download/install.sh | sh

Click the command to select all of it, then copy.

This puts oh-my-shell in ~/.local/bin, and the short name omsh next to it if that name is free (a different file already called omsh is left alone, with a warning). It does not run chsh, does not edit your shell's startup files, and touches /etc/shells only with --add-to-shells.

Each release has a sha256.sum, and the installer and omsh update compare the download with it before using it. That catches a corrupted or truncated download. It does not prove who made the file: the checksum comes from the same GitHub release as the archive, so your trust rests on GitHub and on https. There are no signatures.

Status: version 1.0.0. It is young. Use it from a terminal profile for a while before you make it your login shell; the installers never run chsh.

Then type oh-my-shell. omsh tour is a one-minute walk through the features.

Other ways to install (a .deb package, from source) are in the user guide.

A real session

  • A command that exists is plain, one that does not is red, quotes are yellow, options and arguments are cyan, an existing file is underlined.
  • If a command is not found, a line suggests a similar name.
  • For file commands the panel counts what would be touched: files and folders, total size, how many are outside the current folder or not owned by you, and up to five example paths.
  • Gray text after the cursor suggests the rest of a command from your history, with commands from the current folder first.

Why it is different

Safe

Every typed line is analyzed first. A dangerous one shows what it would touch and asks; rm can move files to a trash, and undo brings them back.

It asks; it does not replace care.

Offline first

No network access on the normal command path. Typing, running commands, completion, history and the safety check make no connection of their own (a test checks that no network socket is created). One caveat: ~user expansion asks the system's account lookup, and on a machine set up with a network account service (LDAP, sssd) that lookup may use the network. The network is used only when you ask: an AI request, omsh update, and an optional daily update check that is off by default.

No telemetry of any kind.

Fast

Fast and small: budgets for start-up, memory and keystroke latency, checked in CI

The numbers are below.

AI, optional

AI is off until you set it up (omsh ai setup). The shell is fully usable without it, and --no-ai switches it off.

? list the biggest files here
The model proposes a plan of up to 8 steps. You see each command with its explanation and risk, and run them only after you confirm.
?? tar -xzf a.tgz
Explains the command flag by flag. Nothing runs.
?? alone, or Alt+?
Explains why the last command failed, from the command and its exit status. The error text is not captured, so it is not sent.
ls -l | ? which is the biggest
Runs ls -l, sends its (truncated, masked) output with the question.
? history what did I run with docker last week
Searches your history in plain words; the answer comes from the local database.

Text that matches the known secret patterns is masked before anything is sent, and keys are kept in the system keyring or a file only you can read.

Eleven crates, about 107,600 lines of Rust

Continuous integration: Format, Clippy with warnings as errors, tests (including the pseudo-terminal tests and an ssh/scp login-shell test), tests with the network off, a performance gate, and cargo deny for licenses.

The test suite runs the same input through this shell and through /bin/sh (dash on Debian and Ubuntu) and compares the output and the exit status; in a few places it follows bash on purpose.

The full table is in the report. The design page explains processes, threads and the fork path and the terminal and signals.

What it does not do

A POSIX-compatible subset, compared with /bin/sh by the tests; syntax it does not support (arrays, [[ ]], ...) is reported with the place marked. -c, scripts and piped input go to /bin/sh, so ssh host cmd and scp keep working.

Non-goals: full bash compatibility; being a terminal emulator; Windows or macOS.

The main ones: keys that arrive in one read together with Ctrl+C are dropped; the analyzer is a list of rules and does not know every dangerous command; masking does not know every kind of secret; there is no proxy support; a cold disk cache and large work trees were not measured; aarch64 was smoke-tested on a CI runner only, not run on our own hardware.

The whole list is in the user guide.
